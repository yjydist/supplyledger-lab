# ADR-004：本地身份托管与宿主机信任边界

- 状态：接受为实施基线；运行验收待 M1、M3、M6
- 关联：`SPEC.md` §§3.3–3.4、4、13.2、17.2、19；T-NET-02/05、T-ID-01–04、T-SEC-01

## 背景与约束

本项目在单台宿主机的 Docker Compose 上学习 Fabric 身份生命周期。业务调用必须由受信 ECert 的 MSP、`supply.userId` 和 `supply.role` 决定；HTTP token、JSON、Header、路径或钱包参数不能自行声明组织、角色或签名者。共享宿主机无法作为抵御其管理员的硬件隔离边界。

## 决策

每组织分别管理 Enrollment CA 与 TLS CA，另为 Orderer 管理客户端设专用 TLS CA。CA registrar、组织 admin、节点、普通业务用户与 TLS 身份分别签发和保管。公共通道 MSP 只包含信任材料、NodeOUs 与必要 CRL，不含私钥。用户本地 MSP 和 TLS 材料留在受控运行目录，真实密钥、registrar secret、token、数据库和备份不进入 Git、公共镜像、构建上下文或脱敏报告。

组织 API 只托管本组织获准的普通业务用户签名身份；本地 token 只映射到这些既有身份，不接受请求指定其他组织钱包。链码仍以实际提交者 ECert 的 MSP 和属性逐函数授权；组织 admin 与无业务属性 client 不因此获得业务写权限。CA 客户端、Peer Gateway、Orderer 管理端和 CCaaS 均验证 TLS 根、用途与 SAN；Orderer 管理端只信任专用管理客户端 TLS CA，不靠跳过证书验证修复连接。

## 取舍与信任声明

本地托管使 M1–M6 能在无云服务、KMS 和生产身份提供商的条件下复现证书签发及业务签名。代价是组织 API 的管理员能够使用其托管用户的私钥代签，本项目不声称能防止这一点。Docker 网络、只读挂载和 Compose secrets 可限制普通容器的可见范围，但可信宿主机或 Docker 管理员能读取卷、替换容器并越过该隔离；单机共享 PostgreSQL 也不是组织间物理隔离证明。

将真实用户签名迁出本地 API 或引入硬件密钥保护会改变部署与用户操作模式，目前没有已确认需求支持该复杂度。本项目只要求跨组织普通用户不能冒充、业务角色不能由请求自称、秘密不会进入公共交付物。

## 验证与重新评估

M1 检查 registrar/节点/用户/TLS 证书用途、属性、SAN、公有 MSP 与私钥路径；M3 用实际链码身份边界测试无属性 client 与 admin；M6 验证 token 仅映射本组织用户且容器无他组织私钥挂载。T-NET-02/05、T-ID-01–04、T-SEC-01 要审查仓库、构建上下文、容器挂载和脱敏日志。M0 的目录规则与 ADR 不能证明证书或 API 权限运行正确。若宿主机管理员不再可信，必须重新定义威胁模型和密钥托管方案，不能仅调整 Compose 网络并宣称已解决。
