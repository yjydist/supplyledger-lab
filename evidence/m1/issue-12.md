## Public certificate inventory used for this issue

The [#9 measured CA-root and HTTPS-service tables](issue-9.md#measured-ca-roots) record the nine CA HTTPS leaves' issuer/root, root SHA-256 fingerprints, SAN, KU/EKU, purpose, service certificate location and public file owner/mode. Each leaf is joined to its root by the named issuer in those tables. The [#10 certificate CSV](issue-10-certificates.csv) provides `issuer`, `ca_root`, `ca_root_sha256`, `san`, `key_usage`, `extended_key_usage`, `purpose`, `cert_path`, `cert_owner_uid_gid` and `cert_mode` for the ten relevant identity leaves: `seller-peer0-tls`, `buyer-peer0-tls`, `carrier-peer0-tls`, `orderer0-tls` through `orderer2-tls`, `orderer0-admin-server-tls` through `orderer2-admin-server-tls`, and `osnadmin-client1-tls`. The [native issuance ledger](issue-10.md) connects those identities to their separate CA commands. This issue reuses those measured public-metadata records rather than copying private files or duplicating 19 rows of metadata. File ownership and mode come from #9/#10's measurements; this #12 verifier checks certificate trust, SAN, KU/EKU and purpose, not current filesystem ownership.

The command's final summary was `PASS: 5 pinned roots, 18 service certificate files, one dedicated admin-client certificate file, one missing-EKU negative control`, followed by `NOT RUN: live Peer/Orderer/admin API/CCaaS handshakes and full T-NET-05`. `make verify-m1-tls` exited 0. The full [trust matrix and M2/M3 wiring requirements](../../docs/m1-tls-trust.md) identify both sides of every path without asserting that the later consumer configuration exists.

OpenSSL `-purpose sslserver` or `sslclient` checks that the certificate allows that use; it does **not** prove exclusive use. The M1 admin-server and admin-client certificates both contain server and client EKUs. Root separation, dedicated issuance custody and the future Orderer admin API's dedicated-only client-root configuration are the management boundary. The verifier demonstrates the first two certificates' chains, not the latter configuration.

During implementation, the first local script run exposed a missing two hex digits in the transcribed dedicated-root fingerprint; after correction, root matching passed. A later run exposed that macOS `/usr/bin/openssl` is LibreSSL and does not provide the required hostname verification option; the verifier now selects an installed OpenSSL 3 executable or accepts `--openssl`. Independent review then exposed that OpenSSL purpose validation permits a leaf with absent EKU and that ordinary root verification does not check the trusted root's self-signature. The explicit EKU rule, negative ECert control, `-check_ss_sig` and restricted CA path/store address those false positives. The final run above is the recorded result. No CA root or identity was changed in response.

## Remaining live acceptance

M2 #16/#18 must render each Orderer admin endpoint with its ordinary Orderer TLS **server** certificate and a client-root list containing only the dedicated admin-client TLS root. A real `osnadmin` request must verify the exact DNS and ordinary server root, present the dedicated client certificate/key, and be contrasted with missing/wrong credentials. M2 #86 must complete full `T-NET-05` using a live Peer or Orderer. M3 #22 must issue separate Peer→CCaaS client credentials and verify the real connection. None of these can be inferred from this offline checker or the existing CA HTTPS test.
